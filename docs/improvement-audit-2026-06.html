What the app is meant to do

The Greyhound Predictor is an end-to-end betting research system for Irish greyhound racing. It scrapes results and race cards from GRI Ireland into SQLite, engineers ~100+ features (form, pace, ELO, trainer/sire, race-relative), trains XGBoost / LightGBM / LambdaRank / sklearn models with Optuna tuning and Platt calibration, serves win/forecast/trio probabilities for upcoming cards, and sizes bets with fractional Kelly against a tracked bankroll. The explicit objective (per backend/program.md) is Kelly ROI > 5% on held-out data while beating the SP-favourite baseline — i.e. the system's product is calibrated probabilities that beat the market, not raw accuracy. Backend deploys to Railway (single container, persistent volume at /app/data/); frontend deploys to Vercel.

Five findings that change everything else (read these first):
  1. Every existing model's metrics are contaminated. Batch-computed training aggregates (trainer/trap/sire win rates, track speed baselines) are computed over all resulted races with no date cutoff — future and own-race outcomes leak into every training row (C1). All experiments need retraining after the fix; expect honest (lower) scores.
  2. One disk failure loses everything. There are no backups of the SQLite DB or model artifacts, the fresh-database migration path is broken, and a previous WAL corruption incident already proved the risk (A1, B1).
  3. The API is completely unauthenticated, including endpoints that wipe bet history, swap the production database file, and trigger unbounded scrapes — behind CORS allow_origins=["*"] (A2–A4).
  4. A GRI markup change would silently zero the data feed. Parse failures, site errors, and "no racing today" are indistinguishable; scrape jobs report success either way (E1, E2).
  5. The staking the user sees was never backtested. Served probabilities are renormalized per race but the backtest uses unnormalized ones; the user's Kelly settings are ignored by both backend and frontend, which each hardcode their own constants (C5, D1).

AData safety & security

The app is internet-reachable with no authentication and no backups, and its only datastore is one SQLite file on one Railway volume holding irreplaceable scraped history (GRI pages age out). These tasks remove the existential risks.

A1 Automated off-site backups of database and model artifacts P0MInfra

Files: backend/app/tasks/scheduler.py, new backend/scripts/backup.py, backend/app/config.py · Depends on: nothing

Problem. No backup mechanism exists anywhere (the only ".bak" in the codebase is created and immediately deleted inside app/api/features.py:734-736). The SQLite DB and trained model artifacts live solely at /app/data/ on one Railway volume. A docstring at features.py:560 records that WAL corruption has already happened once. Volume loss = all scraped history, experiments, predictions, and bankroll records gone permanently.

Implementation. Add a nightly APScheduler job (the scheduler already runs in-process) that: (1) runs PRAGMA wal_checkpoint(TRUNCATE), (2) executes VACUUM INTO '/app/data/backup-tmp.db' (atomic, consistent snapshot — never copy the live file), (3) uploads the snapshot plus a tar of data/models/ to S3-compatible object storage (Cloudflare R2 or Backblaze B2 free tier) using boto3, (4) applies retention (keep 7 daily + 4 weekly), (5) records success/failure in a log table or ScrapeLog-style row. Credentials via new env vars (BACKUP_S3_*) in config.py and .env.example. Also provide scripts/restore_backup.py and document the restore procedure in the README (see J8).

  • A scheduled job produces a dated snapshot in object storage nightly; manual trigger endpoint or script exists.
  • Restore script downloads a snapshot and produces a working DB verified by PRAGMA integrity_check and a row-count smoke test.
  • Backup failure is logged loudly (and surfaces in J5 alerting once available); missing credentials disable the job with a clear startup warning rather than crashing.
  • Model artifacts directory is included; restore round-trip loads one artifact successfully.

A2 Add API-key authentication to the backend P0MBackend

Files: backend/app/main.py, new backend/app/auth.py, backend/app/config.py, frontend/src/api/client.ts · Depends on: nothing

Problem. Not a single endpoint has any auth dependency (verified across all 11 routers in app/api/). Anonymous callers can wipe bankroll history (POST /bankroll/reset, bankroll.py:111), delete experiments/features/schedules, swap the production database file (features.py:557, see A4), trigger unbounded multi-year scrapes of GRI (scraping.py:403), and start unlimited concurrent training jobs that can OOM the container (training.py:62,139).

Implementation. Create a FastAPI dependency that checks an X-API-Key header against settings.api_key (new env var, generate a long random value in Railway). Apply it globally via app.include_router(router, dependencies=[Depends(require_api_key)]) for every router; leave /api/health open. If API_KEY is unset, log a prominent warning and allow (preserves local dev ergonomics) — but document that production must set it. Frontend: read VITE_API_KEY in client.ts and attach the header via an axios default. Document both env vars.

  • With API_KEY set, every /api/* route except /api/health returns 401 without the correct header and works with it.
  • Frontend works end-to-end against an auth-enabled backend using VITE_API_KEY.
  • A TestClient test asserts 401 on a sample of destructive endpoints (bankroll reset, experiment delete, scrape trigger) without the key.
  • .env.example and README document both variables.

A3 Fix CORS: wire configured origins, drop wildcard + credentials P0SBackend

Files: backend/app/main.py:35-41, backend/app/config.py:8 · Depends on: nothing

Problem. main.py hardcodes allow_origins=["*"] together with allow_credentials=True — an invalid and unsafe combination. The settings.cors_origins setting (and the CORS_ORIGINS env var documented in .env.example) is never read, so an operator who sets it believes they've restricted origins when nothing changed. The config default itself also ends with "*".

Implementation. Use allow_origins=settings.cors_origins; remove "*" from the default list (keep the two localhost entries); set the real Vercel URL via the Railway env var. Keep allow_credentials=True only with the explicit list.

  • grep shows no "*" in CORS configuration; settings.cors_origins is the only source.
  • Frontend on the configured Vercel origin works; a request from an unlisted origin is blocked by the browser (no ACAO header echoed).
  • Setting CORS_ORIGINS env var demonstrably changes the served header.

A4 Remove the database rebuild/swap endpoint P0SBackend

Files: backend/app/api/features.py:555-768 · Depends on: A1 recommended first (so an admin path to reclaim space still exists)

Problem. DELETE /api/features/computed/all disposes the engine, renames the live DB aside, swaps in a rebuilt file, and deletes the backup (features.py:735). It hand-rolls DDL that can drift from the models, and any in-flight request can re-create pool connections to the renamed file mid-swap (split-brain/corruption). It was written for a one-off recovery incident that has passed. Combined with no auth, it is a single-request data-loss vector.

Implementation. Delete the endpoint (and its frontend caller if any). If feature-table cleanup is still wanted, replace with a bounded DELETE FROM computed_features WHERE version_id IS NULL + PRAGMA incremental_vacuum/offline VACUUM admin script under scripts/, never deleting backups.

  • The route no longer exists; OpenAPI schema confirms.
  • Any UI affordance that called it is removed or repointed at the safe cleanup.
  • A safe cleanup path (script or guarded endpoint) is documented for reclaiming space.

A5 Harden the feature sandbox (timeout is a no-op in threads) P1MBackend

Files: backend/app/services/feature_sandbox.py, backend/app/api/features.py:528-549 · Depends on: A2

Problem. The sandbox runs user-supplied Python via RestrictedPython but re-enables type and a whitelisted __import__ (feature_sandbox.py:44-89) — RestrictedPython is known-bypassable with these. Worse, the 5-second timeout uses SIGALRM, which only works on the main thread; feature materialization runs the sandbox in a background thread, where signal.alarm raises ValueError, is caught at :138, and the timeout silently does nothing. An infinite-loop feature runs forever; a memory bomb OOMs the container.

Implementation. Execute user feature code in a subprocess (e.g. multiprocessing.Process or subprocess + JSON over stdio) with a hard join(timeout) kill and resource.setrlimit caps on CPU and address space. Remove type from the builtins whitelist. Batch entries per subprocess invocation to amortize startup (one process per feature per materialization batch, not per row). Auth (A2) is the prerequisite layer; this contains what authenticated users (or a leaked key) can do.

  • A seeded test feature containing while True: pass is killed within the timeout when run through the materialization path (background thread), not just the request path.
  • A memory-bomb feature (e.g. growing a list to GBs) is killed by the rlimit without taking down the API process.
  • All existing seeded code features still compute identical values (regression-tested on a sample dog history).
  • type is no longer exposed; sandbox builtins are covered by a unit test pinning the whitelist.

BDatabase & migrations

The schema currently has two competing sources of truth (Alembic and create_all() in seed scripts), a migration that fails on modern Alembic, and a hardcoded DB path in the migration config. Disaster recovery does not work today — verified empirically.

B1 Repair the migration chain; make Alembic the single schema authority P0LInfra

Files: backend/alembic/versions/c3f8a1d42b7e_*.py, new catch-up migration, backend/scripts/seed_tracks.py:171, backend/scripts/seed_features.py:598, backend/scraping/backfill.py:67 · Depends on: J2 (pin Alembic) recommended alongside

  • The resulting schema contains all 15 tables including bankroll_config and bet_records with all current columns and indexes.
  • No create_all() remains outside tests (grep verified); app boots and seeds correctly on both a fresh DB and a copy of the existing prod schema.

B4 SQLite busy_timeout and write-contention hygiene P1SBackend

Files: backend/app/database.py · Depends on: nothing

Problem. Scrape threads, training threads, APScheduler jobs, and API requests all write to one SQLite file. WAL allows concurrent readers but one writer; the pragma hook (database.py:18-29) sets WAL/synchronous/cache but not busy_timeout, so concurrent writers fail instantly with database is locked instead of queueing. Pool settings (pool_size=10, max_overflow=20) advertise parallelism SQLite can't deliver.

Implementation. Add PRAGMA busy_timeout=30000 in set_sqlite_pragma. Trim the misleading pool kwargs (SQLite file DBs gain nothing from large pools). Document the single-writer constraint at the top of database.py. (Larger refactors — a write queue or Postgres — are out of scope here; this removes the immediate failure mode.)

  • PRAGMA busy_timeout returns 30000 on a connection from the app engine (unit test).
  • A two-thread concurrent-write test (insert loops) completes without OperationalError: database is locked.

B5 Reconcile ORM ↔ migration drift so autogenerate is trustworthy P2MInfra

Files: backend/app/models/*.py, backend/app/database.py · Depends on: B1

Problem. Three composite indexes exist only in migrations, not in models (ix_computed_features_def_entry, ix_races_status_track_distance, ix_scheduled_run_schedule_date); models declare FKs the DB intentionally lacks (races.last_scrape_log_id, race_entries.last_scrape_log_id, computed_features.version_id). Implementation. Declare the composite indexes in __table_args__; resolve each phantom FK (add via batch migration or remove from the model with a comment); add the standard SQLAlchemy naming_convention dict to Base.metadata; document "always use alembic revision to generate IDs" in CLAUDE.md.

  • alembic revision --autogenerate against a fully-migrated DB produces an empty migration (and CI asserts this — wire into J1).
  • Composite indexes appear in model __table_args__; naming convention is set.

CML correctness — leakage, evaluation, calibration

The prior train/serve-skew audit (PR #44) fixed the first layer of leakage; these findings are the next layer down. C1–C4 invalidate current experiment metrics and should be fixed before trusting any model comparison. A full retrain of active experiments is the final step of this section.

C1 Fix training-time leakage in batch aggregate features (+ retrain) P0LML

Files: backend/ml/race_features.py:610-861, 1435, backend/ml/dataset_builder.py:149 · Depends on: nothing; do before any new experiments

Problem. The batch path used by training (compute_builtin_features_batch) builds its lookup tables — trap win rates (:610-634), going-conditional trap rates (:641-663), trainer win/place rates (:669-723, which also drops the 90-day window the single-entry path applies), sire stats (:729-778), track average times (:782-800), speed-figure baselines (:805-861) — over all resulted races with no date cutoff. Every training row's aggregate features therefore include the row's own race outcome and all future races, including the test period. The single-entry path used at predict time correctly threads before_date, so this is simultaneously target leakage and train/serve skew. All current CV/test metrics are inflated by an unknown amount.

Implementation. Make each aggregate time-aware: fetch the raw event rows once (entry, date, group key, outcome), sort by date, and build cumulative counters so a lookup returns "stats strictly before this row's race_date" — the same pattern the per-dog history aggregates and ELO already use in this file. Apply the same 90/180-day windows the single-entry helpers document, so train and serve compute identical values. At minimum, the entry's own race must be excluded from every aggregate. Then retrain all active experiments (the audit script scripts/audit_experiments_for_post_race_features.py shows the precedent for sizing blast radius) and record the new honest baselines.

  • Regression test (see C15): computing batch features for a fixed entry, then adding a later race for the same trainer/trap/sire/track, leaves the entry's features bit-identical.
  • For a sample of entries, batch-path values equal single-entry-path values (same windows, same cutoffs) within float tolerance.
  • Existing tests pass; new experiments trained post-fix store a flag or version marker distinguishing them from contaminated ones.
  • Active experiments retrained; README/experiment notes record that pre-fix metrics are not comparable.

C2 Sort datasets chronologically; fix walk-forward CV and LambdaRank groups P0MML

Files: backend/ml/dataset_builder.py:119, 505-580, backend/app/services/training_service.py:575-590 · Depends on: nothing

Problem. The dataset query orders by Race.race_date.desc() with no secondary key and is never re-sorted. Two consequences: (1) generate_walk_forward_fold_indices assumes ascending order; with descending input the embargo check discards every validation race, all folds come back empty, and training silently falls back to single-split — walk-forward CV has never actually run in production (its test uses ascending data, so it passes). (2) Same-date races can interleave (no stable secondary sort), so LambdaRank group sizes computed by _compute_group_sizes (:558-580) can fragment across races — corrupting ranking groups, relevance normalization, and per-race metrics, silently.

Implementation. After assembly, sort the dataset ascending with race contiguity — entries_df.sort_values(["race_date", "race_id"]) (plus trap for determinism) — and reindex X/y/meta to match. Add an assertion in _compute_group_sizes that race_ids are grouped-contiguous, and a monotonicity assertion (or internal sort) in the fold generator.

  • New test feeds a descending-date dataset through fold generation and gets non-empty, chronologically valid folds (train max date < val min date, embargo respected).
  • New test asserts group contiguity holds for a synthetic multi-race same-date dataset, and that the assertion fires on interleaved input.
  • Walk-forward training on real data produces > 0 folds (verify via training log) instead of the silent single-split fallback.

C3 Stop autoresearch selecting on the test set P0MML

Files: backend/ml/autoresearch.py:254-266, 300-306, 333-387, 527-535 · Depends on: C2 (for walk-forward objectives)

Problem. The autonomous experiment loop evaluates every candidate config on X_test and accepts/rejects on test-set metrics (betting_kelly_roi etc.). Running up to 100 mutation trials and keeping the test-set maximizer is textbook test-set mining: the reported best score is meaningless and the chosen config will regress live. It also burns the test set for all subsequent experiment comparisons. Bonus bug: it builds datasets with default impute_missing=True, so GBM configs are selected under a different NaN policy than run_training later uses.

Implementation. Score proposals on the validation split (or walk-forward folds once C2 lands); keep the test set untouched during the loop; evaluate only the final winner on test, once, and report it separately. Pass _nan_policy_for(algorithm) through to dataset building so selection and final training match.

  • No accept/reject decision in the loop reads a test_* metric (code inspection + a unit test on the objective extraction).
  • Final report contains exactly one test-set evaluation, labelled as such.
  • NaN policy during search matches the policy run_training would use for that algorithm.

C5 Unify probability normalization between backtest and serving P1MML

Files: backend/app/services/prediction_service.py:595-599, 243-293, backend/app/services/training_service.py:282-305, backend/ml/evaluation.py, backend/ml/trainers/lambdarank_trainer.py:227-235 · Depends on: pairs well with G1

Problem. Serving divides calibrated probabilities by their per-race sum; training evaluation and compute_betting_metrics never normalize. So the backtested ROI was computed on different numbers than the Kelly stakes users see — if a race's probabilities sum to 0.85, serving inflates each by ~18%, manufacturing unvalidated edge. The LambdaRank trainer does the opposite (calibrates after softmax, refuses to renormalize, with an incorrect comment claiming renormalization could change the top pick — division by a common positive sum is monotonic). Confidence/entropy math (:243-293) also assumes a proper distribution it doesn't always get.

Implementation. Standardize on per-race normalization as the final step in both paths: apply it inside compute_betting_metrics (group by race_id) and in training-eval metrics, identical to serving. Evaluate calibration (reliability/Brier) on the post-normalization probabilities. Fix the LambdaRank comment and make its output consistent with the convention. Compute entropy/margins on the normalized vector.

  • A test predicts one synthetic race through the serve path and through the betting-metrics path with the same artifact and asserts identical probabilities.
  • All races' served win probabilities sum to 1.0 ± 1e-6 across all four trainer types.
